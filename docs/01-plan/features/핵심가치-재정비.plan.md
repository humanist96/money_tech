## 0. 조사 방법과 핵심 진단

12개 병렬 에이전트로 전수 조사(프론트/데이터레이어/크롤러/정량방법론/DB/문서/루트잡동사니) 후 3개 설계안을 생성하고, 2개 검증 에이전트(실현가능성·완결성)가 실코드 대조로 교차 검증했다. 검증에서 확인된 사실:

1. **핵심가치는 코드가 증언한다** — 전 파이프라인(수집→NLP→가격→평가→MV)이 `predictions` 테이블로 수렴하고, 프론트 7개 화면이 전부 이 테이블의 뷰다. 문서 5세대(기획.md → enhancement → 추가컨텐츠 v2 → advancement → 수익화)에서 비전이 계속 바뀌는 동안 "예측을 검증한다"는 축만 불변이었다.
2. **그러나 핵심 지표가 깨져 있다** — `price_collector.py:119,137`이 과거 언급에 오늘 가격을 일괄 기입(look-ahead), `prediction_evaluator.py:52-72`가 1w/1m/3m 전 구간에 "스크립트 실행일 현재가"를 기록, 적중 기준이 0% 임계(evaluator)와 ±3%(fix_historical_prices)로 이중화. **현재 hit_rate/trust_score는 해석 불가능한 수치다.**
3. **보안 결함 4건 (public 저장소)** — §3 Phase 0 참조. 오늘 즉시 조치 대상.
4. **"전일 등락 원인 분석"은 기존 기획 5세대 어디에도 없는 공백 영역** — /briefing은 전일 *영상 내용* 요약일 뿐, *시장 등락의 원인 규명*이 아니다. 신규 컨텐츠로 타당.

> 참고: 세션에 연결된 whymoved MCP(카카오 커넥터)를 실호출 검증했다. 출력 구조(factors: disclosure/flow/market + sources)는 우수해 설계 표준으로 차용하되, 세션 스코프 인증이라 GitHub Actions 크롤러에서 재사용 불가하며 등락률 계산 버그(+26.8% 오표기)도 확인되어 **가격 수치는 반드시 자체 데이터로 계산**한다.

## 1. 핵심가치 정의

> **"한국 금융 크리에이터(유튜버·블로거·텔레그램·애널리스트)의 종목 예측 발언을 자동 수집하고, 사후 가격으로 검증한 적중률 트랙레코드를 공개하는 유일한 서비스."**

| 근거 | 내용 |
|---|---|
| 데이터 흐름의 수렴점 | 모든 파이프라인이 predictions 테이블 하나로 수렴 — 코드 구조 자체가 핵심을 증언 |
| 문서 3세대의 일관성 | 비전이 세 번 바뀌어도 "적중률 검증" 축은 불변 |
| 대체 불가능성 | 컨센서스·감성·버즈는 타 서비스로 대체 가능하지만, 종단 트랙레코드는 축적 기간 자체가 진입장벽 |

**전략 제1원칙: 기능을 늘리는 게 아니라, 측정을 믿을 수 있게 만든다.** 아래 트랙 A의 CUT은 전부 트랙 B(측정 재구축)에 재투자할 유지보수 시간의 재원이다.

## 2. 트랙 A — 기능 재정비 (CORE / KEEP / MERGE / CUT)

판정 기준: **CORE** = 핵심가치 사슬(수집→감지→평가→트랙레코드)에 직접 기여 / **KEEP** = 저비용 보조 / **MERGE** = predictions의 변형 뷰라 독립 존재 이유 없음 / **CUT** = 무관·취약·리스크.

## 3. 트랙 B — 정량 분석 고도화 (측정의 재구축)

### 3.0 설계 원칙

- **측정 시점의 진실성이 최우선**: P(t0)와 P(t0+h)라는 전제부터 복구한다. 이것이 깨진 상태의 통계 기법은 전부 무의미
- **점수는 적게, 정직하게**: 노출 지표는 hit rate(Wilson CI) + 평균 초과수익 2개만. Brier(확률 예측 없음)·Sharpe(포트폴리오 아님)는 기각
- **정의 변경은 evaluation_version으로 추적**: 서로 다른 정의가 같은 컬럼에 섞이는 사고(0% vs ±3%)를 구조적으로 차단
- **1인 × 3주 스코프**: 감지기 전면 개편·미국주식 소스·실시간 평가는 명시적 제외

### 3.1 현행 결함 (실코드 검증 완료)

### 3.2 시간 규약과 벤치마크

- 모든 날짜 **KST** 통일. **t0** = 콘텐츠 발행일. 주식은 t0 당일(휴장 시 직전 거래일) 종가, 코인은 t0 일자 CoinGecko 일별 종가(KRW)
- 평가일 = t0 + h (h ∈ {7, 30, 90}). 가격은 **항상 asset_prices / benchmark_prices 히스토리 테이블에서 날짜로 조회** — "평가 스크립트가 돈 날"은 어떤 경우에도 사용 금지. 히스토리 공백은 +3일 이내 최근접 허용, 그 밖은 `outcome='unevaluable'` 명시 기록
- 벤치마크: KOSPI 상장→KOSPI 지수, KOSDAQ 상장→KOSDAQ 지수(pykrx `get_index_ohlcv`), 알트코인→BTC/KRW. 시장 소속은 asset_dictionary.market 1회 백필
- **BTC 자체는 절대수익 + push 밴드 2배**로 판정하고, **리더보드에 채널별 BTC 예측 비중을 표기**해 척도 혼합을 가시화한다(검증 지적: BTC 강세장에서 "BTC 사라" 반복 채널의 기계적 상승 방지 — 완전 해소는 아니므로 비중 표기가 필수 완충)

### 3.3 판정 규칙 (evaluation_version = 2)

```
r_asset = P(t0+h)/P(t0) − 1,  r_bench = B(t0+h)/B(t0) − 1,  excess = r_asset − r_bench
```

| 유형 | hit | miss | push (표본 제외) |
|---|---|---|---|
| buy | excess > +band(h) | excess < −band(h) | \|excess\| ≤ band(h) |
| sell | excess < −band(h) | excess > +band(h) | \|excess\| ≤ band(h) |
| hold | \|excess\| ≤ band(h) | \|excess\| > band(h) | — |

- band(h): 거래비용·노이즈 흡수 — **1w ±1.5%, 1m ±2.5%, 3m ±4%** (evaluator_v2.py 상단 상수, 변경 시 version 증가)
- direction_score 가중평균(0.5/0.3/0.2) **폐기** — 호라이즌별 독립 저장·독립 집계. 리더보드 기본 1m, 1w/3m 탭
- **헤징 차단**: 같은 (video, asset)에 buy·sell 공존 시 둘 다 모순 예측으로 평가 제외. 유니크 제약을 (video_id, mentioned_asset_id)로 강화하되, **nlp_pipeline.py:291의 INSERT ON CONFLICT 대상 교체를 같은 배포 단위로 묶는다**(검증 지적: 인덱스만 먼저 넣으면 크롤러 잡 전체가 예외로 실패)
- **상장폐지는 unevaluable이 아니다**(검증 지적 — 생존편향 차단): 상폐·거래정지 종목의 buy는 **miss**(정리매매 최종가 기준, 근사 excess −100%), sell은 **hit**. 원인 불명의 수집 실패만 unevaluable

### 3.4 목표가 판정 (애널리스트)

현행 "12개월 목표가 vs 1개월 가격 이탈률" **폐기**. 대체: (a) TP > P(t0)이면 buy로 간주해 §3.3과 동일 방향 판정 — 증권사도 유튜버와 같은 척도, 매수 편향은 벤치마크 조정으로 상쇄. (b) 목표가 진행률 `clamp((P(t0+90)−P(t0))/(TP−P(t0)), −1, 2)`은 정보성 표기만(랭킹 미반영). 12개월 도달 평가는 데이터 축적 후.

### 3.5 통계적 신뢰도

- **랭킹 키 = Wilson 95% 신뢰구간 하한(wilson_low)** — 표본이 적으면 하한이 자동으로 내려가 승자의 저주 완화. trust_score 공식 폐기, channels.trust_score에 wilson_low 저장(프론트 호환)
- **유효 표본**: push·unevaluable·is_duplicate 제외. **30일 내 동일 (channel, asset, type) 반복은 is_duplicate**(첫 언급만 계상, 방향이 바뀌면 새 베팅)
- 표기 기준: n<10 리더보드 제외("평가 중 n/10" 배지), 10≤n<30 "표본 적음" 배지, n≥30 정상
- 노출 지표 2종: `적중률 58% (95% CI 44–71%) · 평가 32건 · 평균 초과수익 +1.8%p`. 초과수익 표준편차(IR용)는 내부 저장만

### 3.6 의미 전달층 (검증 지적 반영 — "정교함"을 "의미"로 번역)

- **예측 단위 판정 증거 카드**: 예측 상세에서 t0 가격 → t+h 가격 → 벤치마크 수익률 → excess → 판정을 드릴다운 표시. 지표를 신뢰하게 만드는 것은 숫자가 아니라 추적 가능한 증거다
- **평이한 등급 병기(대중용)**: wilson_low > 0.5 → "시장보다 잘 맞힘", CI가 0.5 포함 → "시장 수준", n<10 → "판단 유보". 숫자는 전문가용, 등급은 대중용 이중 표기
- 채널 상세에 유형별 분해(buy/sell/hold 건수), 평가 불능 n건(사유별), push n건 표기 — 선택 편향의 가시화

### 3.7 데이터 품질

- **Point-in-time 원칙**: 평가 경로의 모든 가격은 히스토리 테이블 날짜 조회. 외부 API는 "히스토리 적재" 시에만

## 4. 트랙 C — 전일 등락 원인 분석 컨텐츠 (`/movers`)

### 4.0 포지셔닝

- **공백 확인**: 기존 기획 5세대 어디에도 없음. /briefing은 "전일 크리에이터가 뭐라고 했나"(발화 요약), /movers는 "전일 시장이 왜 움직였고, **크리에이터 말이 맞았나**"(시장 사실 + 검증). 방향이 반대이므로 별도 페이지 + 상호 링크
- **차별화의 전부는 creator 블록이다**: "3주 전 ○○채널이 매수 예측 → 오늘 +12% 적중 방향". 공시+수급+뉴스 요약만 남으면 네이버 금융 복붙과 다를 게 없다 — 따라서 선정 로직을 뒤집는다(§4.1)
- **하드 게이트(검증 지적)**: creator 블록의 "적중" 라벨은 **트랙 B evaluator_v2 + 백필 완료 후에만 출고**. 그 전에 출시하려면 적중 라벨 없이 "언급 사실"만 표시하는 축소 모드 — 오염된 trust_score로 "검증되지 않은 검증 결과"를 내보내면 핵심가치를 정면 훼손

### 4.1 대상 종목 선정 (크리에이터 우선 — 검증 지적 반영)

1. **1순위 후보군**: 최근 30일 크리에이터 언급 종목 중 전일 |등락률| ≥ 5% 또는 거래대금 전일비 3배 이상 — "우리 데이터가 있는 종목"이 주인공
2. **보조 후보군**: KOSPI/KOSDAQ 등락률 상위(종가 ≥ 1,000원, 거래대금 ≥ 50억, 관리종목 제외 — pykrx 전 종목 스냅샷)
3. 스코어: 등락률 0.42 / 거래대금 급증 0.26 / 언급 수 0.21 / 언급 채널 다양성 0.11 (crowd_sentiment 신호는 트랙 A CUT과 충돌하므로 제외, 가중치 재정규화 — 검증 지적 반영)
4. 카드 수는 6~12개 가변. **creator evidence 보유 비율 60% 미만이면 카드 수를 줄여서라도 차별화 밀도 유지** — "우리만 쓸 수 있는 카드 6장"이 "남들도 쓰는 카드 14장"보다 낫다. 출시 전 최근 30영업일 백테스트로 충족률 측정

### 4.2 근거 수집 (evidence[] 통일 구조: {type, summary, source_url, source_date})

| type | 소스 | 비고 |
|---|---|---|
| disclosure | DART Open API `list.json` (D-3~D, 가격영향 유형 필터: 잠정실적·공급계약·유증/CB·최대주주변경·자사주·무증·소송·감자) | **신규 시크릿 DART_API_KEY(무료, 일 20,000건)** — P0 첫 작업. corpCode.xml 주 1회 → dart_corp_map 캐시 |
| flow | pykrx `get_market_trading_value_by_date` — 외인/기관 순매수 ±100억 이상 | 16:40 시점 외인 잠정치는 "추정" 표기, 익일 backfill 시 갱신 |
| news | 네이버 뉴스 검색 API (기존 NAVER_CLIENT_ID/SECRET 재사용), D-1 15:30~D 15:30 기사 제목+요약 최대 5건 | 원문 스크래핑 안 함(봇차단 회피) |
| market | 당일 KOSPI/KOSDAQ ±2% 이상이면 코드가 무조건 주입 | LLM 오귀인 완화 |
| creator | 우리 DB 교차 (아래) | **유일 차별점** |

creator 교차 쿼리는 **신 평가 스키마 기준으로 작성**(검증 지적 — 구 direction_* 컬럼은 트랙 B에서 폐기됨):

```sql
SELECT c.name AS channel_name, c.channel_type, cs.wilson_low, cs.n_effective,
       p.prediction_type, p.created_at, v.title, v.published_at,
       pe.outcome, pe.excess_return, p.evaluation_status
FROM predictions p
JOIN channels c  ON c.id = p.channel_id
JOIN videos v    ON v.id = p.video_id
JOIN mentioned_assets ma ON ma.id = p.mentioned_asset_id
LEFT JOIN prediction_evaluations pe
       ON pe.prediction_id = p.id AND pe.horizon = '1m' AND pe.evaluation_version = 2
LEFT JOIN channel_stats cs
       ON cs.channel_id = c.id AND cs.horizon = '1m' AND cs.evaluation_version = 2
WHERE ma.asset_code = $1 AND p.created_at >= NOW() - INTERVAL '90 days'
  AND NOT p.is_duplicate
ORDER BY cs.wilson_low DESC NULLS LAST, p.created_at DESC LIMIT 10;
```

verdict 표기: 평가 완료 건은 outcome(hit/miss), 미도래 건은 "방향 일치(평가 전)"로 구분 — 트랙 B가 세운 엄밀한 정의를 movers가 무르지 않는다.

### 4.3 LLM 합성 (gpt-4o-mini, llm_analyzer.py 패턴 재사용 — JSON mode, temp 0.1)

출력: `{headline(20자), cause_type(earnings|contract|capital_change|supply_demand|news_theme|market_wide|creator_driven|unexplained), summary(3문장), factors[{type, description, evidence_refs[]}], creator_context, confidence}`

**환각 방지 5장치(코드 레벨)**: ① evidence_refs가 입력 근거 번호의 부분집합인지 후처리 검증(위반 factor 드롭) ② factors 비었는데 unexplained가 아니면 강제 치환 ③ 지수 ±2% 시 market factor 자동 주입 ④ confidence는 서버 재계산(disclosure 포함 2유형↑=high, 1유형=medium, news/creator만=low) ⑤ 투자 자문 아님 disclaimer 고정 부착

### 4.4 스키마·크론·파일 구성

- **019_daily_movers.sql**: `daily_movers`(trade_date, stock_code UNIQUE, close/change_pct/value_ratio, selection_reason, headline, cause_type, summary, confidence, factors JSONB, evidence JSONB, creator_context JSONB, investor_flow JSONB) + `dart_corp_map`(stock_code PK, corp_code). evidence는 일 6~12행·행 단위 조회라 JSONB가 관례 부합
- **`.github/workflows/movers.yml` 분리 신설**: `cron "40 7 * * 1-5"`(KST 16:40, 종가·수급 확정 후) + workflow_dispatch(date 입력, 백필용). crawl.yml에 안 붙이는 이유: 실행 조건이 다르고 crawl.yml은 타임아웃 만성 이력. `--backfill-days 3` 자가치유(compute_stats 패턴 차용)
- 파일: `crawler/movers_main.py`(진입점·upsert 멱등) / `movers_selector.py` / `dart_client.py` / `movers_evidence.py` / `movers_analyzer.py` — 각 400줄 이하, db.py·logger.py·http_util.py 재사용

### 4.5 프론트

- **`/movers` 신규**: 날짜 셀렉터(기본 최근 영업일) · 상승/하락/관심 탭 · MoverCard(종목·등락률·배지 → headline → summary → factors 아코디언(출처 외부링크) → **CreatorContext 블록**(채널 상세·영상 내부링크) → confidence 배지 → disclaimer)
- 대시보드 "어제 왜 움직였나" TOP3 카드, /briefing 상단 요약 스트립 1줄, /assets/[code]에 과거 movers 타임라인 재사용
- `frontend/lib/queries/movers.ts` + `app/api/movers/route.ts`(revalidate 600). 추후 api/v1/movers로 B2B 노출 여지

### 4.6 비용·실패 모드

- 비용: gpt-4o-mini 일 ~12콜(~$0.005) → **월 $1 미만**. DART/네이버 무료 한도의 0.1% 미만. Actions 일 ~5분
- 휴장일: pykrx 빈 DF → exit 0. 프론트는 getLatestMoversDate()로 최근 영업일 표시
- KRX 미확정: 스냅샷 행 수가 정상치(~2,600종목)의 50% 미만이면 저장 없이 실패 exit → 익일 backfill 보완
- DART/뉴스 실패: 해당 유형만 누락 진행(재시도 1회+백오프) — 근거 유형이 줄면 confidence 자동 하향
- LLM 실패: 규칙 기반 템플릿 fallback("공시 N건, 외인 N억 순매수 확인") + cause_type='unexplained'
- pykrx는 비공식 스크래핑 기반 — 행 수 검증 게이트로 완화, 장기적으로 KRX 공식 API 전환 검토
