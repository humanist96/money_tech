## 6. 교훈 (Lessons Learned)

### 6.1 잘 된 점 (Keep)

1. **계획 문서의 실명성** — "기능 20개가 한 테이블의 변형 뷰" 진단이 코드 인벤토리로 입증되어, 리다이렉트 12경로를 신뢰하고 실행할 수 있었음. 12개 병렬 에이전트 전수 조사가 근거 확보에 결정적.

2. **점-in-시간(point-in-time) 원칙의 복구력** — look-ahead 오염 5년치가 있었지만, 평가 경로를 테이블 히스토리로 재설계하면서 신뢰할 수 있는 지표로 완전히 복구 가능함을 증명. 정의를 바꾸는 것이 아니라 측정 방식을 옳게 하는 것의 차이.

3. **하드 게이트의 구조적 강제** — 계획서의 "플래그"보다 구현의 "조인 술어(prediction_evaluations v2 행 존재)" 이 훨씬 실패 방지가 탄탄함. 코드 리뷰 단계에서 이런 차이를 포착하고 개선한 것이 숨은 성과.

4. **프로덕션 검증의 중요성** — /movers 하드 게이트가 "계획보다 견고"해진 이유는 실제 배포하면서 노출된 데이터 일관성 문제를 수정했기 때문. 가상 설계만으로는 노출 불가능.

### 6.2 개선할 점 (Problem)

1. **Match Rate 79.9%는 계획의 실행 강도 미달을 드러냄** — 90% 기준치는 초과했지만 "거의 다 했다"는 착각 방지. 특히 트랙 B는 70.7%로 정량분석의 근간인 "적중 정의"가 여전히 v1/v2 공존 상태. 갭 분석 후 재수렴이 필수임을 명시한 바 타당.

2. **P0 갭 중 G2, G4는 분석 당일에 고치지 못한 이유** — 둘 다 "프론트 전면 수정" 범주라 우선순위가 밀렸지만, 다음 PDCA에서는 P0/P1 구분을 명확히 하고 P0는 배포 전 완료 원칙 강제 필요.

3. **트랙 B 백필이 외부 API 조회를 포함하면서 3주 예상 기간 지체 가능성** — CoinGecko 무료 한도(분당 30콜)를 고려해 데모 키 발급·체크포인트형 재개 등 구체적 계획을 세웠으나, 1년 이전 코인 예측은 unevaluable 명시로 표본 급감 우려. 공백기 UX가 핵심.

4. **/movers 프론트 미완성의 영향** — 백엔드·스키마는 완성했지만 카드 렌더링·날짜 셀렉터·API 라우트 3개 줄이 남아, 코어 피처의 외면성이 낮음. 크리에이터 블록(차별화의 전부)이 비어 있는 상태로 출시 시 가치 절반 이상 손실.

### 6.3 다음에 적용할 것 (Try)

1. **계획 vs 구현 대조를 매주 1회 정기화** — 이번엔 분석을 종료 시점에 한 번 했지만, 트랙별 진행 상황이 불균형(A 86%, B 71%)일 때 조기 감지 가능. 트랙 간 피드백 루프 단축.

2. **P0/P1 구분을 명확히 하고 P0는 배포 게이트로 강제** — 이번 Act 1차에서 G1, G3은 수정했지만 G2, G4는 여전히 미해결. 프로덕션 배포 전 리스트를 명시적으로 만들 것. 특히 "지표를 직접 훼손하는" P0 는 수치로 검증 불가능할 때 배포 보류.

3. **설계 단계에서 "구현 방식의 안전성" 검토** — 하드 게이트의 사례처럼, 계획의 "플래그 전환"이 구현에선 "조인 술어"로 견고해진 예. 이런 개선을 사후 수정이 아니라 설계 리뷰 때 예상할 수 있게 체크리스트 마련.

4. **외부 API 의존성은 스코프 문서에 명시 + 백업 계획** — CoinGecko, pykrx, DART 등이 모두 외부라서, "히스토리 적재"로 일원화한 설계는 좋았지만, 데모 키 발급·fail-safe 테스트를 계획 단계에서 선행.

5. **리더보드 공백기 UX를 "신뢰 구축 스토리"로 전환** — 백필 후 표본 급감은 음수가 아니라 "구 방법론이 얼마나 깨져 있었나"를 증명하는 긍정 신호. 커뮤니케이션 각본을 미리 작성.
