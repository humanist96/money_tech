## 3. 핵심 발견 3가지

### 발견 1: 평가 파이프라인 3개월 정지와 5단계 복구 (§13)

**문제**: eval_date가 2026-05-13에서 정지 (3개월 공백)

**원인**:
1. `backfill_prices.py`가 수동 CLI (자동 크론 경로 부재)
2. `crawl.yml`이 오늘 1행만 적재 (미완료 평가 재수렴 로직 없음)
3. **휴리스틱 오판**: `have_recent >= 15`가 최근 80일 공백을 "already loaded"로 판정

**복구 5단계** (커밋 26ad8d9):
1. 백필 휴리스틱 수정 (`have_recent >= 15` → 더 신중한 조건)
2. `requeue_unevaluable()` 구현 — unevaluable 래칫 제거
3. evaluate 배선 — CI 자동 실행 경로 추가
4. G7 범위 교체 — 미완료 v2 평가 조인 추가
5. `crawl.yml` gap-repair 단계 — 자가복구 크론

**결과**:
- **eval_date: 05-13 → 08-02** (복구 확인)
- **확정 판정: 5,490 → 10,255** (+86.8%)
- **랭크 채널: 1 → 70개** (+69배)
- **평가 완료율: 71.6% → 88.2%**

**교훈**: "측정 도구 자체를 검증해야 한다" — 차용된 코드의 자가복구 로직이 없으면 오작동이 영구화된다.

### 발견 2: 벤치마크 오배정 2건과 "시장 상회" 서사의 반전 (§14, §17.3)

**G40 — 시장 매핑 82% 누락**

```
asset_dictionary에 market 보유: 76개 (18%)
평가 대상 한국 종목: 429개
NULL → KOSPI 강제 배정: 353개
실제 KOSDAQ: 140개
영향: 906건 (적중률 예측 −5%p)
```

수정: `asset_dictionary` 전수 백필 + `requeue_stale_benchmarks` 1,025건 재판정
- KOSPI 커버리지: 18% → 100%
- KOSDAQ 적중률: 38.1% → 47.2%

**G41 — 미국 종목 KOSPI 판정**

```
NASDAQ·NYSE 종목: 32개
오배정 평가: 859건 (KOSPI 벤치마크)
정상 판정 후: 0건
미국 종목 적중률: 48.1~54.9% (정상 범위)
```

수정: NASDAQ/S&P500 지수 도입 + 6자리 숫자 가드 추가

**"시장 상회" 서사의 반전**:
- **3차**: 0개 (시장 수준 37, 시장 하회 21)
- **G40 후**: **2개** (멘토링하우스, 힐링여행자)
- **G41 후**: **0개 재귀**
- **6차 재측정**: **3개** 다시 출현 (모두 n<30, "표본 적음")

**분석**: 오배정이 만든 허상이었다. 미국주식이 KOSPI로 재어질 때만 상회하는 채널이었다. 하지만 6차에서 3개 재출현은 데이터 재평가의 자연스러운 변동이며, 표본 크기 주의만으로 충분.

### 발견 3: 정직한 결론 — 오배정 교정 후에도 50% 미달, 측정 도구 검증이 사양에 없었다

**적중률 변화**:
- 초판 측정(G40·G41 미교정): 37.3%
- G40·G41 교정 후: 40.4%
- **여전히 50% 미달**

**판정별 분해** (§17.6):
| 판정 기준 | 적중률 |
|---|---:|
| 절대수익(BTC 자체) | **54.9%** ← 정상 신호 |
| NASDAQ | 49.7% |
| KOSDAQ | 47.2% |
| BTC | 45.7% |
| **KOSPI** | **36.8%** ← 시장 저퍼폼 |

**호라이즌별 성적**: 1주 44.9% → 1개월 38.8% → 3개월 32.3%

**결론**:
- "크리에이터는 절대 방향 적중은 50% 이상이나, 시장을 상회하는 종목 선정은 못 한다"

## 7. 교훈 (Lessons Learned)

### 잘 된 점

1. **계획 문서의 실명성과 전수 조사**
   - "기능 20개가 predictions의 변형 뷰"라는 진단이 12 에이전트 코드 인벤토리로 입증됨
   - 리다이렉트 12경로를 신뢰하고 삭제할 수 있었던 이유

2. **점-in-시간(point-in-time) 원칙의 복구력**
   - look-ahead 오염 5년치가 있어도 테이블 히스토리로 평가 경로 재설계하면 완전히 복구 가능
   - 정의를 바꾸는 것이 아니라 측정 방식을 옳게 하는 것의 차이

3. **하드 게이트의 구조적 강제**
   - 계획의 "플래그 전환"보다 구현의 "조인 술어" (prediction_evaluations v2 행 존재)가 훨씬 실패 방지 강력
   - 코드 리뷰 단계에서 이런 개선을 포착했던 것이 숨은 성과

4. **운영 복구의 자가복구 패턴**
   - 5단계 수정(휴리스틱·unevaluable·배선·범위·CI 게이트)을 통해 차용 코드의 자가복구 능력 확보
   - 한 번 중단된 파이프라인의 재개를 위해 **원점 복구보다 자동화 경로가 중요**

### 개선할 점

1. **Match Rate 79.9% < 90% — 계획 실행 강도 미달**
   - 90% 기준은 초과했지만 "거의 다 했다"는 착각 방지 필요
   - 트랙 B 70.7%는 정량분석의 근간인 "적중 정의"가 여전히 v1/v2 공존 상태였음을 드러냄

2. **P0 갭 중 G2, G4는 분석 당일에 고치지 못한 이유**
   - 둘 다 "프론트 전면 수정" 범주로 우선순위 밀림
   - 다음 PDCA에서 P0 구분을 명확히 하고 배포 게이트로 강제해야 함

3. **점수와 실재의 괴리**
   - 대장이 계획 조항 단위라서 "벤치마크 매핑 1줄이 오배정 1,765건을 대표"
   - 150항목 체크리스트가 정량적 데이터 품질을 측정할 수 없음
   - **측정 도구(gap analysis 자체) 자체를 검증해야 한다**

4. **사양 갭이 코드 갭보다 오래 남음**
   - §3.6 "시장 상회 0개 시 사용자 고지" 5회 연속 미처리
   - 코드는 옳았으나 사양에 없어서 쓸 수 없었음
   - 계획서 갱신이 코드 수정만큼 중요

### 다음에 적용할 것

1. **계획 vs 구현 대조를 매주 1회 정기화**
   - 이번은 종료 시점에 한 번만 했으나, 트랙 간 불균형 조기 감지 필요
   - "A 86% vs B 71%" 불균형이 중점 투자 신호

2. **P0/P1 구분을 명확히 하고 P0는 배포 게이트로 강제**
   - G1, G3는 수정했지만 G2, G4는 프론트 전면 수정이라 미루어짐
   - 프로덕션 배포 전 P0 리스트 체크 의무화

3. **외부 API 의존성은 스코프 문서에 명시 + 백업 계획**
   - CoinGecko(분당 30콜), pykrx(지수 인증), DART 등
   - "히스토리 적재"로 일원화한 설계는 좋았으나, fail-safe 테스트를 계획 단계에서 선행
   - 이번 pykrx 제거는 계획 변경이었으나 문서 미갱신(§17.9)

4. **리더보드 공백기 UX를 "신뢰 구축 스토리"로 전환**
   - 백필 후 표본 급감은 음수가 아니라 "구 방법론이 얼마나 깨져 있었나"를 증명
   - 커뮤니케이션 각본을 미리 작성해 "공백"을 "검증"으로 프레이밍

5. **측정 도구의 정기적 외부 검증 필수화**
   - 이번 벤치마크 검증(§14)이 없었다면 오배정 1,765건을 그대로 발표할 뻔했음
   - gap analysis 자체에 대한 "gap analysis" 프로세스 도입
